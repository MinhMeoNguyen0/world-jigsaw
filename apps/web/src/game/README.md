# Private-local game adapter

`LiveGame` is an unmounted transport/state adapter. It does not provide game controls or establish that the reviewed frontend is playable. It expects the private game service at the same origin. The reviewed visual draft remains in its existing owner's custody.

Create a `LiveGame`, subscribe to its state, and call `connect()`. The adapter verifies the definition checksum and requests the versioned WebSocket subscription. Its snapshot, allowance, own turn, draft revision, sequence and active previews are captured at one ordered handoff. Render `game.snapshot` as canonical and `previews` as temporary overlays; remove overlays on clear, disconnect or resynchronization. Clear the displayed board when `game` is null. Editing is available only while the connection is `ready`. Call `disconnect()` when finished, and call `connect()` after a dropped connection.

Call `begin()` to open a turn. Call `heartbeat()` periodically while the UI is using a turn, before its `expiresAt`. `newAction()` creates an ID for one independently counted move; retain that ID for adjustments to the same move. Provide complete group membership and canonical source revisions. For a join request, provide the union of moving and target members and source revisions; the server decides whether to join and authors the resulting component. A moved group is one action. The UI can show immediate pointer movement locally but must treat it as provisional.

Send another preview only after `previewPending` clears. The server broadcasts previews for rendering and sends the submitting socket a separate receipt for the accepted action set and draft revision. An unrelated broadcast, stale receipt, rejection, socket send, or timeout does not establish acceptance. A rejected or uncertain submission triggers resynchronization; a recovered nonempty draft must be canceled before editing or confirming, since it may include another tab's work or a lost submission. A lost receipt remains pending until reconnect or cancellation. `undo(actionId)` removes a pending independent action; the server may reject dependent undo.

`confirm()` creates a command only after the latest submission is acknowledged, and sends the exact accepted action set and revision. A concurrent same-session mutation makes the server reject a stale confirmation. A successful response is durable. Retain `pendingConfirm` for an unknown response and retry the same payload or use `resolveConfirm()`; pending, unknown, and expired do not mean success. A consumer that needs reload recovery must persist `pendingConfirm` and call `restorePendingConfirm()` before allowing edits. Clear it only after a known confirmed or rejected result. `cancel()` retries the same request ID after an ambiguous response. Cancel can report another tab's confirming command; use `resolveCancelCommand()` before editing. Confirmed allowance comes from the service, not local move counting.

The v2 stream extension is negotiated by `subscribe.v2`; existing v1 messages remain closed and continue to work. Identity changes invalidate affected v2 subscriptions, which reconnect for a fresh atomic handoff. Unsupported or regressing messages and board event gaps also trigger resynchronization. This adapter does not integrate the visual draft, chat, or touch controls, and does not resolve the remaining frontend geometry and image-rights work.
