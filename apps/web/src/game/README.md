# Private-local game adapter (integration pending)

`LiveGame` is an unmounted transport/state adapter. It does not change the current page, provide game controls, or pass the multiplayer gate. It expects a game service and UI at the same private origin. The reviewed visual draft remains under its existing owner's custody. These adapter tests use a simulated service; they are not evidence of a playable game or end-to-end synchronization.

## Use by the eventual UI

Create a `LiveGame`, subscribe to its state, and call `connect()`. A connection is usable only after state becomes `ready`: the adapter creates/renews a session, checks the `CurrentGame` board and definition checksum, and installs the WebSocket subscription snapshot and active previews. Render `game.snapshot` as canonical and `previews` as temporary overlays, removing the latter on clear, disconnect, or resync. A preview is never a save. A committed event updates the canonical board and triggers a fresh snapshot to refresh allowance and turn. An event gap or unsupported frame also requires resync. Call `disconnect()` when the adapter is no longer needed. A dropped connection is visible as `disconnected`; call `connect()` to reconnect. Until the fresh subscription arrives, do not permit editing.

Call `begin()` and use `newAction()` once for each independently counted move; preserve its action ID for every adjustment. Supply complete group membership and canonical source revisions in each action. On a join request, supply the union of moving and target group members and source revisions; the server decides whether to join and authors the resulting component. Send a preview only after the preceding one is no longer `previewPending`. The UI can render immediate pointer movement locally, but must treat it as provisional and roll it back on rejection or cancel. The adapter sends heartbeats while a turn is active. Errors, busy pieces, and connection loss appear in `issue`. `undo(actionId)` is for a pending action; the server may reject dependent undo. `cancel()` retries the same request ID after an ambiguous response, clears only after the server responds, and refreshes the latest board. A lost in-flight preview or a turn acquired by another adapter instance makes the draft uncertain: cancel it before editing.

`confirm()` sends only the latest server-authored action set. It creates one command ID and retains the exact payload after an ambiguous response, so calling it again retries the same command. `resolveConfirm()` queries that ID; pending, unknown, and expired do not mean success. A consumer that needs reload recovery must retain `pendingConfirm` from state and call `restorePendingConfirm()` before allowing edits; this module intentionally adds no storage layer. Clear that retained payload only after a known confirmed or rejected result. Cancel can report a different tab's confirming command; use `resolveCancelCommand()` before editing. If Cancel reports such an outcome without a command ID, the draft remains uncertain and needs reconciliation. Confirmed allowance comes from the service, not local move counting. The UI may show an explicitly provisional count but must not infer authoritative charges from action kinds.

## Required reconciliation before integration or merge

The shared schemas and reducers on merged main and backend object `fb16527f64677171734261e06bec3ed03915118d` were inspected read-only. The handoff's reported backend review head `5f01abfe065680f65ad5753d3fe08f296a9033b1` was not present as a Git object at implementation time. The backend owner must compare the final reviewed wire against this adapter, especially session creation, HTTP responses, subscription handoff, action membership and revisions, server-authored actions, generation changes, undo, cancellation, command lookup, and sequencing.

In the inspected service, outgoing preview sequences are independent of submitted sequences, and an accepted preview has no submitted-sequence acknowledgement. This adapter serializes its own preview submissions and pauses its own heartbeat while one is pending; it treats the next newer server-authored frame for that action and turn as its acknowledgement. This assumes only one adapter writes a given identity's turn, with no other tab or queued unsolicited frame for that action. The contract permits shared tabs, so that assumption is **not sufficient for safe general integration**: a delayed or other-tab frame can falsely acknowledge a submission. Reconcile an explicit correlated acceptance/receipt or another provably safe protocol with the backend owner before enabling this adapter in the game. Likewise, the service exposes no submitted-sequence watermark on reconnect; a newly created adapter cannot safely continue an existing turn and instead requires cancel. The reconnect behavior of an already active instance also assumes no other tab submits on its turn.

Finally, agree on geometry/snap vectors, provisional move display, a cleared locally served image, and same-origin setup; integrate with the preserved reviewed frontend only through its authorized custody path. The actual two-browser gate, including attachment, cancellation, refresh, competing edits, and lost/retried Confirm, remains required. No backend or frontend pipeline branch was modified by this adapter.
