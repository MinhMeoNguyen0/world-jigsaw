# World Jigsaw shared contract v1

This is the first local integration contract, not a working game, a deployed service, or a production puzzle generator. `v1/schema.json` is the source of truth (JSON Schema draft 7); `v1/types.d.ts` is generated with `pnpm --filter @world-jigsaw/contracts generate`. It contains reusable `$defs` for HTTP payloads as well as a top-level WebSocket envelope union. Java and browser implementations consume the same JSON and fixtures. Run `pnpm --filter @world-jigsaw/contracts test`. `validate(type, value)` checks shape and selected cross-field invariants; `validateBoard(definition, snapshot)` additionally checks identity, membership and reciprocal adjacency. They are not a game engine, authorization, complete geometry validation, or a Unicode 15.1 chat validator. The server must enforce every invariant below regardless of client validation.

The v1 fields and engineering defaults below are selected for local integration, not additional captain decisions. Routes are interface targets, not existing endpoints. Geometry, snapping and the current frontend prototype require review with the generator and game owners before importing real content. Fixture square pieces are synthetic and do not establish production artwork, snapping tolerance or distribution.

## Identity, versioning and geometry

All identifiers are UUIDs; revisions, sequences and generations are nonnegative JSON safe integers. Zero is allowed. IDs are stable within their documented scope and never recycled in that scope: puzzle globally, piece within a puzzle definition, group within a puzzle (new ID when a merge/split creates a new group), action within a turn, event within a puzzle, and command/request within a recognized identity. A recognized identity is an opaque game-owned anonymous subject, not a verified human; session credentials are never exposed in game events. `POST /api/v1/session` sets an HttpOnly, host-only, SameSite cookie (Secure on HTTPS) and returns `Session`. The authenticated browser obtains `ChatAssertionResponse` from `POST /api/v1/session/chat-assertion`; its short-lived signed assertion has claims matching `ChatAssertionClaims` and a chat-only audience. The browser presents it only to the chat service over a protected transport; do not log it. Signature algorithm, trust/key rotation, authentication, revocation and public security review remain service-owner work; claims JSON is not itself authentication. Game and chat use separate databases and credentials, with no cross-database transaction or table reads. A game must continue when chat is down. One host and one active game writer are the local baseline; infrastructure is optional and not a game dependency.

Each message carries `schemaVersion: 1`, and unknown versions or unrecognized durable event types require resync/upgrade, never silent interpretation. V1 schemas are closed objects: senders cannot add fields under v1. A breaking or additive wire change requires a new version and explicit negotiation; immutable existing version semantics and fixtures remain available. Times are RFC 3339 UTC (`Z`); dates are UTC calendar dates. Never represent 64-bit database integers outside JavaScript's safe range as JSON numbers.

A definition is immutable per `(puzzleId, definitionVersion)` and its checksum is SHA-256 of the RFC 8785 canonical UTF-8 JSON of the complete definition with the `checksum` member omitted, encoded as lowercase `sha256:<hex>`. A consumer verifies the checksum before using a definition. Coordinates are integer thousandths of a puzzle-space unit, bounded to ±1,000,000,000. Bounds are solved-picture bounds, not a clipping boundary for the workspace; negative coordinates are permitted. Each piece's edge path is in local piece coordinates and follows its contour in order; adding `solvedPosition` gives the solved coordinate. Edges are reciprocal by piece/edge identity and share reversed solved geometry. Rotation is clockwise degrees about the puzzle-space origin, followed by translation; the allowed rotation list constrains group transforms. The three-square fixture uses only zero rotation. A group transform applies to solved coordinates of every member, so membership has one canonical group and no per-piece position copy. Anchored means in final position and immovable; confirmed does not imply anchored. The engine must validate closed, non-self-intersecting geometry, adjacency, matching shared edges, bounds, transforms, snap/anchor tolerance, and image rights. The schema/validator does not establish those properties or verify the checksum.

A canonical snapshot holds every defined piece exactly once in a unique group, with unique group IDs and revisions, even for loose pieces (a one-piece group). Board versions are monotonic per puzzle. `GET /api/v1/game/current` returns `CurrentGame` from a consistent read, or structured `PUZZLE_UNAVAILABLE`; it never silently serves yesterday. Allowance is committed state; sum of used and remaining is five. The client derives provisional counts separately. `ownTurn` is null when absent; a session may share its quota and turn across tabs.

## Batch and live stream

`POST /api/v1/game/turns` takes `BeginTurn` and returns `Turn`. One open turn per recognized identity and puzzle; 30-second renewable exclusive leases on all touched groups, heartbeat every 5 seconds, 30-second disconnect grace. A successful `Heartbeat` returns `LeaseRenewed` with the server expiry; socket failures use `SocketError` and HTTP failures use `ErrorResponse`. Acquiring all affected groups for an attach is atomic or returns `PIECE_BUSY`; a generation fences old owners. One existing connected group costs one pending action; a newly introduced piece costs one. Repeat adjustment of the same action is free. A join costs no additional action; two independently introduced actions retain both counts. Action dependencies are acyclic IDs from the same batch; undo removes the selected action and transitive dependents, their provisional slots and overlay. `POST /api/v1/game/turns/{turnId}/undo` takes `Undo` and returns `UndoResult`; it fences the old generation, clears it for all clients, then re-emits surviving actions under the returned new generation. The owner and engine must validate affected membership, base revisions and intended geometry; a client assertion is not authority. An action that returns to the same canonical state incurs no confirmed charge. Five actions can still be adjusted when the allowance is fully projected.

`Confirm` is submitted to `POST /api/v1/game/turns/{turnId}/confirm`; the entire batch, its quota charge, board version/event and idempotent outcome commit atomically or none do. Stale revision, invalid geometry or insufficient quota reject without charge; return a structured error and resynchronize the latest board. `CommandResult` returns a durable confirmed result only after commit. An absent reply is unknown: retry the identical payload and command ID or query `GET /api/v1/game/commands/{commandId}` in the identity scope. Same identity, command ID and RFC 8785 canonical JSON payload returns the same outcome; a changed payload yields `COMMAND_CONFLICT`. The service retains outcomes or non-reusable tombstones for its documented retry horizon; an expired ID must never execute again as a new command. Exact retention policy remains open. `pending`, `unknown` and `expired` are distinct from rejection and confirmation.

`Cancel` goes to `POST /api/v1/game/turns/{turnId}/cancel`, serialized against Confirm. If cancel wins, clear the overlay and reveal the latest canonical positions, never restore an old snapshot. If confirm has won or is processing, return the actual outcome/command ID; losing a response is not proof of cancellation. Retry a lost Cancel with the same identity, request ID and canonical payload; reuse with a different payload conflicts. A processing Confirm pins its generation until commit or known rollback even if its lease expires. Unused committed allowance remains available later that UTC day; confirmed undo is outside v1.

On authenticated, origin-checked `GET /api/v1/game/stream`, send `Subscribe` with null cursor for a fresh snapshot or the last applied board version. `Subscribed` provides an internally consistent snapshot and equal watermark, plus active overlays at the handoff; a server must buffer or replay across the snapshot/stream boundary so no committed change is lost. If a cursor cannot be served, send `ResyncRequired`. `PreviewSubmit` is an advisory request; `Preview` is server-authored, temporary and never a canonical write or completion. Sequences increase per turn generation, may be coalesced, and a receiver applies only newer frames. `PreviewCleared` fences the generation permanently, even if old frames arrive later. Reconnect reconciles active overlays; restart clears them, reloads the board and communicates draft loss, but resolves an in-flight Confirm by its original ID first. Bound frame size, rate and queues; slow consumers resync rather than block writes.

`BoardChanged` is emitted only after durable commit; apply only the next puzzle board version, deduplicate repeated versions/event IDs, and resync on gaps or conflicting duplicates. Replace the indicated groups and remove `removedGroupIds` atomically; validate the resulting complete snapshot. The event stream is at-least-once, not exactly-once. Snapshot and event version are separate from preview sequence. `PuzzleChanged` with null puzzle and `available: false` signals missing content, never yesterday's board.

At UTC midnight the authoritative service closes the old puzzle. A Confirm admitted before close may finish after midnight; a not-yet-admitted preview clears without charge. Unknown old-puzzle commands are resolved against that old puzzle by the original ID. A missing new puzzle is temporarily unavailable. Lifecycle locking and clock implementation need integration tests; the schema does not prove atomicity or timing.

## Ephemeral chat

Chat is a separate live global room with no transcript, history, offline delivery or replay. `ChatSend` and `ChatMessage` carry an ephemeral message ID and text; server acceptance (`ChatAccepted`) means accepted for relay, not delivered to all peers. Chat identity uses the audience-scoped assertion above, not the game cookie or game database. Do not log/store message bodies. Enforce a 1,024-byte UTF-8 transport limit before normalization, plus rate/fanout bounds. Normalize NFC, trim Unicode 15.1 White_Space at the ends, reject Unicode Cc controls in the original input (including tabs/newlines), reject empty text, then count at most 40 Unicode 15.1 extended grapheme clusters including spaces, punctuation and emoji. Fixtures in `v1/fixtures/chat-text.json` are shared vectors; ICU4J 74.2 is the chat owner's proposed pinned Unicode 15.1 implementation. Browser counts are advisory and must use the same pinned data. Use safe text rendering. Chat failure is displayed independently of game play. No user-facing delivery guarantee follows from acceptance.

`scenarios.json` is a handoff of behavioral oracles for future engine and integration tests, including the UTC boundary; this package does not implement transactions, a service clock, network delivery, or pinned Unicode segmentation. The Node test exercises representative chat vectors against its runtime segmenter only and does not prove full Unicode 15.1 conformance.
