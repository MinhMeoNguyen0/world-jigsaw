# World Jigsaw shared contract v1

This is the first local integration contract, not a working game, a deployed service, or a production puzzle generator. `v1/schema.json` is the source of truth (JSON Schema draft 7); `v1/types.d.ts` is generated with `pnpm --filter @world-jigsaw/contracts generate`. It contains reusable `$defs` for HTTP payloads as well as a top-level WebSocket envelope union. Java and browser implementations consume the same JSON and fixtures. Run `pnpm --filter @world-jigsaw/contracts test`. `validate(type, value)` checks shape and selected cross-field invariants; `validateBoard(definition, snapshot)` additionally checks identity, membership and reciprocal adjacency. They are not a game engine, authorization, complete geometry validation, or a Unicode 15.1 chat validator. The server must enforce every invariant below regardless of client validation.

The v1 fields and engineering defaults below are selected for local integration, not additional captain decisions. Routes are interface targets, not existing endpoints. Geometry, snapping and the current frontend prototype require review with the generator and game owners before importing real content. Fixture square pieces are synthetic and do not establish production artwork, snapping tolerance or distribution.

## Identity, versioning and geometry

All identifiers are UUIDs; revisions, sequences and generations are nonnegative JSON safe integers. Zero is allowed. IDs are stable within their documented scope and never recycled in that scope: puzzle globally, piece within a puzzle definition, group within a puzzle (new ID when a merge/split creates a new group), action within a turn, event within a puzzle, and command/request within a recognized identity. A recognized identity is an opaque game-owned anonymous subject, not a verified human; session credentials are never exposed in game events. `POST /api/v1/session` sets an HttpOnly, host-only, SameSite cookie (Secure on HTTPS) and returns `Session`. The authenticated browser obtains `ChatAssertionResponse` from `POST /api/v1/session/chat-assertion`; its short-lived signed assertion has claims matching `ChatAssertionClaims` and a chat-only audience. The browser presents it only to the chat service over a protected transport; do not log it. Signature algorithm, trust/key rotation, authentication, revocation and public security review remain service-owner work; claims JSON is not itself authentication. Game and chat use separate databases and credentials, with no cross-database transaction or table reads. A game must continue when chat is down. One host and one active game writer are the local baseline; infrastructure is optional and not a game dependency.

Each message carries `schemaVersion: 1`, and unknown versions or unrecognized durable event types require resync/upgrade, never silent interpretation. V1 schemas are closed objects: senders cannot add fields under v1. A breaking or additive wire change requires a new version and explicit negotiation; immutable existing version semantics and fixtures remain available. Times are RFC 3339 UTC (`Z`); dates are UTC calendar dates. Never represent 64-bit database integers outside JavaScript's safe range as JSON numbers.

A definition is immutable per `(puzzleId, definitionVersion)`; its checksum is SHA-256 of RFC 8785 canonical UTF-8 JSON excluding `checksum`, as lowercase `sha256:<hex>`. Verify it before use. Coordinates are integer thousandths of a puzzle-space unit (x right, y down), bounded to ±1,000,000,000. `imageBounds`, `playSurface` and `workspace` are distinct rectangles; the surface uses `[min,max)` on both axes, and the transformed `referencePoint` of a loose piece classifies its position. Viewport scale, zoom and resize never change puzzle coordinates. The engine enforces workspace and verifies contours and checksums; this package does not. Initial transforms come from one authoritative saved snapshot, never per-browser randomization. Import receives the authoritative UTC day separately, atomically associates it with the unique puzzle UUID/day record and immutable definition version/checksum, and validates exactly one group membership per piece; the client clock and board version do not determine the puzzle day.

Edges follow the contour in local piece coordinates using `line` or `cubic` segments. `solvedPosition` maps these into solved puzzle coordinates. Adjoining edges have reciprocal IDs and reversed matching solved geometry, including reversed control points. The immutable definition includes generator version, seed and shape settings. The captain's current prototype settings are 100/340/60 permille for tab depth/width/wave; fixtures are examples, not proof of a production generator. Tuning creates a new draft definition/version/checksum before activation; it cannot change active geometry per client.

A group transform rotates solved coordinates clockwise around the puzzle-space origin and then translates. Angles are integer millidegrees in `[0,360000)`. For a visible pivot `c` and change `Δ`, update translation as `c - R(Δ)c + R(Δ)t`; canonical rounding and snap tolerances still require cross-language owner agreement. Pre-completion, a previously correct assembled group may move or rotate as one counted action; `finalPosition` is geometry-derived canonical status, not a permanent lock, and is recomputed on Confirm. Preview cannot complete a board. What interaction is allowed after the entire puzzle completes remains in existing review; no post-completion policy is decided here.

The frontend's sample contour collision algorithm (16 segments per cubic, 18 world units overlap at piece width 100 (the later prototype replaced 8)) is provisional, not an exact penetration bound or authoritative cross-language algorithm. Owners must agree on touching, overlap, rounding and concurrent collisions using shared vectors before integration. The engine validates authoritative geometry, snap and collisions.
A canonical snapshot holds every defined piece exactly once in a unique group, with unique group IDs and revisions, even for loose pieces (a one-piece group). Board versions are monotonic per puzzle. For progress, count each piece once if its group is connected (more than one member), including groups away from the image. Preview never changes canonical progress. `GET /api/v1/game/current` returns `CurrentGame` from a consistent read, or structured `PUZZLE_UNAVAILABLE`; it never silently serves yesterday. Allowance is committed state; sum of used and remaining is five. The client derives provisional counts separately. `ownTurn` is null when absent; a session may share its quota and turn across tabs.

## Batch and live stream

`POST /api/v1/game/turns` takes `BeginTurn` and returns `Turn`. One open turn per recognized identity and puzzle; 30-second renewable exclusive leases on all touched groups, heartbeat every 5 seconds and 30-second disconnect grace. `Heartbeat` returns `LeaseRenewed`; errors use `SocketError` or `ErrorResponse`. Acquiring all affected groups for attachment is atomic or returns `PIECE_BUSY`; a generation fences old owners.

For this local v1 baseline a `sort` is an uncharged movement of a loose outer-table piece that remains outside the play surface. It is broadcast as a temporary preview with the same lease/revision checks and may be included in an explicitly confirmed atomic batch at zero charge, including a sort-only batch. Entering the surface promotes the same pending action ID to `piece`, costing one provisional move. Returning an unjoined pending entry to the outer table demotes it to sort; a joined action cannot be demoted while it remains joined. Moving or rotating an eligible previously confirmed piece/group is one `piece`/`group` action, regardless of member count. Re-adjustment adds no charge; joining costs none and preserves two independently counted action IDs. An action ending at the same canonical state costs zero. The server validates history, membership, base revisions, zone, eligibility and intended geometry; client-supplied `kind` is advisory and cannot set cost. At most five actions can be counted; remaining allowance may impose a lower limit. Five pending counted actions can still be adjusted. Surface entry is based on authoritative starting state and accepted action history, not an asserted physical pointer path.

Undo removes one selected pending action and its provisional slot and overlay only if the server can remove it without invalidating the remaining batch. If actions have joined or otherwise depend on the selected action, the server rejects undo without changing the batch; the player can cancel the batch instead. `POST /api/v1/game/turns/{turnId}/undo` takes `Undo` and returns `UndoResult`; it fences the old generation, clears it for all clients, then re-emits surviving actions under the returned new generation. Cancel removes all provisional actions and never writes stale locations.
`Confirm` is submitted to `POST /api/v1/game/turns/{turnId}/confirm`; the entire batch, its quota charge, board version/event and idempotent outcome commit atomically or none do. Stale revision, invalid geometry or insufficient quota reject without charge; return a structured error and resynchronize the latest board. `CommandResult` returns a durable confirmed result only after commit. An absent reply is unknown: retry the identical payload and command ID or query `GET /api/v1/game/commands/{commandId}` in the identity scope. The command ID is unique within recognized identity across puzzles; puzzle ID is part of the RFC 8785 canonical JSON payload. Same identity, command ID and canonical payload returns the same outcome; a changed payload yields `COMMAND_CONFLICT`. The service retains outcomes or non-reusable tombstones for its documented retry horizon; an expired ID must never execute again as a new command. Exact retention policy remains open. `pending`, `unknown` and `expired` are distinct from rejection and confirmation.

`Cancel` goes to `POST /api/v1/game/turns/{turnId}/cancel`, serialized against Confirm. If cancel wins, clear the overlay and reveal the latest canonical positions, never restore an old snapshot. If confirm has won or is processing, return the actual outcome/command ID; losing a response is not proof of cancellation. Retry a lost Cancel with the same identity, request ID and canonical payload; reuse with a different payload conflicts. A processing Confirm pins its generation until commit or known rollback even if its lease expires. Unused committed allowance remains available later that UTC day; confirmed undo is outside v1.

On authenticated, origin-checked `GET /api/v1/game/stream`, send `Subscribe` with null cursor for a fresh snapshot or the last applied board version. `Subscribed` provides an internally consistent snapshot and equal watermark, plus active overlays at the handoff; a server must buffer or replay across the snapshot/stream boundary so no committed change is lost. If a cursor cannot be served, send `ResyncRequired`. `PreviewSubmit` is an advisory request; `Preview` is server-authored, temporary and never a canonical write or completion. Sequences increase per turn generation, may be coalesced per action, and a receiver applies only newer frames. On subscription or reconnect the server provides the latest active preview for each action in increasing sequence order; it must not omit an action merely because another action has a later sequence. A full overlay is transient and never a durable event. `PreviewCleared` fences the generation permanently, even if old frames arrive later. Reconnect reconciles active overlays; restart clears them, reloads the board and communicates draft loss, but resolves an in-flight Confirm by its original ID first. Bound frame size, rate and queues; slow consumers resync rather than block writes.

`BoardChanged` is emitted only after durable commit; apply only the next puzzle board version, deduplicate repeated versions/event IDs, and resync on gaps or conflicting duplicates. Replace the indicated groups and remove `removedGroupIds` atomically; a merge removes all superseded groups and introduces a new group ID with validated complete membership and revision, and the same transaction updates quota, version, event and result; validate the resulting complete snapshot. The event stream is at-least-once, not exactly-once. Snapshot and event version are separate from preview sequence. `PuzzleChanged` with null puzzle and `available: false` signals missing content, never yesterday's board.

At UTC midnight the authoritative service closes the old puzzle. A Confirm admitted before close may finish after midnight; a not-yet-admitted preview clears without charge. Unknown old-puzzle commands are resolved against that old puzzle by the original ID. A missing new puzzle is temporarily unavailable. Lifecycle locking and clock implementation need integration tests; the schema does not prove atomicity or timing.

## Ephemeral chat

Chat is a separate live global room with no transcript, history, offline delivery or replay. Use `POST /api/v1/chat/messages` with `ChatSend` and `GET /api/v1/chat/stream` as SSE. SSE uses event name `message` and `ChatMessage` data with `messageId`, `displayName`, `sentAt` and text. `ChatAccepted` is an HTTP 202 relay-acceptance response, not proof of peer delivery. Ignore `Last-Event-ID`; reconnect starts empty. Use a streaming browser `fetch` with an Authorization Bearer header and SSE parser: native EventSource cannot send this header. No token in URL, messages or logs. On expiry close the stream, obtain a fresh assertion and reconnect. Proxy must preserve Authorization and avoid SSE buffering.

The game-owned assertion is a compact JWT at most 2,048 characters, with signed `schemaVersion:1`, `iss`, lowercase UUID `sub`, exact `aud=world-jigsaw-chat`, signed `displayName`, integer `iat`/`exp` and lowercase UUID `jti`. Local v1 accepts Ed25519 (`alg=EdDSA`, `typ=JWT`) with configured `kid`, trusted SPKI key and issuer; `iat <= now < exp`, with lifetime and age at most 300 seconds and no skew. Verify offline; reject unknown keys/algorithms, unsupported `nbf`, malformed or duplicate claims and invalid signatures with generic 401. One active key with controlled restart is a prototype boundary; rotation, revocation, replay prevention and public security review remain open. The session's assertion response expiry must match the signed `exp`. Display names are NFC, Unicode 15.1 whitespace-trimmed, free of original Cc, 1–40 Unicode 15.1 extended graphemes and at most 128 UTF-16 code units. JSON Schema's string length is only a shape bound and does not validate these rules.

On POST, reject Unicode Cc in the original input, normalize NFC, trim Unicode 15.1 White_Space, then require 1–40 extended grapheme clusters. Browser checks are advisory; both sides need pinned Unicode 15.1 data. There is no fixed text or request-body limit in this contract: a valid grapheme can contain arbitrarily many code points. Actual transports have finite resource limits and can reject requests they cannot carry with `MESSAGE_TOO_LARGE` (413); such a failure does not imply that the text exceeds 40 graphemes. Use safe text rendering and never log or store message bodies. The relay retains no retry receipts: a retry may be delivered again. No subscribers yields 503; bounded queues prevent slow clients from blocking the relay.

HTTP errors use `ErrorResponse` with required server-generated lowercase UUID `requestId` independent of input. `INVALID_REQUEST`→400, `UNAUTHENTICATED`→401, `FORBIDDEN`→403, `NOT_FOUND`→404 for unknown routes, `METHOD_NOT_ALLOWED`→405 for unsupported methods and `MESSAGE_TOO_LARGE`→413 are non-retryable; `CHAT_UNAVAILABLE`→503 and `INTERNAL_ERROR`→500 are retryable. Generic messages contain no token or content. After an SSE response is open, failure closes the stream; it cannot change the HTTP status. Separate chat database/credentials remain required, without synchronous DB writes for relay; chat outages do not block game. These are local defaults to coordinate with service owners, not deployment or security claims.
`scenarios.json` is a handoff of behavioral oracles for future engine and integration tests, including the UTC boundary; this package does not implement transactions, a service clock, network delivery, or pinned Unicode segmentation. The Node test exercises representative chat vectors against its runtime segmenter only and does not prove full Unicode 15.1 conformance.
